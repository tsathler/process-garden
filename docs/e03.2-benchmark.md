# E03.2 benchmark and stability checks

The benchmark is a separate Godot `SceneTree` script. It builds the environment,
`DemoSnapshotSource`, `ProcessRegistry`, `ProcessSelector`, and `GardenController`
without the normal main scene or interface. It uses a fixed seed and the same
two-second synthetic snapshot cadence for each scenario.

## Measurements

Each scenario row reports:

- Rendered frames, average FPS, minimum rolling FPS, and frame-time average,
  p95, and maximum. Frame time is measured between process-loop observations;
  engine frame processing time is reported separately from Godot's monitor.
  Frame deltas and engine processing time are also split into the sample
  immediately after a synthetic source tick and samples without a source tick.
- Godot static memory at the start, end, and sampled peak, in MiB.
- Maximum scene-tree nodes, orphan nodes, represented creature nodes, and
  tracked process records.
- Accepted and invalid snapshots, complete synthetic tick time (average, p95,
  maximum), and the largest sampled frame with and without a preceding source
  tick.
- DEMO metric updates, lifecycle changes, snapshot copying, and its contract
  validation, each with average and maximum.
- JSON serialization and the same parser used by the HTTP client, including
  JSON decoding and contract validation, each with average and maximum. The
  benchmark performs this round trip to represent the real HTTP ingestion path;
  it is an explicit harness cost and is reported separately.
- Registry acceptance, registry record-list materialization, GardenController
  input copying, selection, creature reconciliation, and the total synchronous
  snapshot callback, each with average and maximum.

The DEMO source emits validated dictionaries, so it does not itself parse
wire-format JSON. The benchmark omits the parser's private cached timestamp,
converts each contract snapshot to UTF-8 JSON, then passes it through
`SnapshotParser.parse_body()` before registry acceptance. This isolates the
real client's parse/validation cost from synthetic snapshot generation. The
parser stage includes both JSON decoding and contract validation; it does not
include HTTP socket or operating-system scheduling time. Profiling timers are
opt-in and disabled in the normal application.

Memory and node monitors are debug-build metrics; [Godot's Performance
documentation](https://docs.godotengine.org/en/4.7/classes/class_performance.html)
notes that static memory is unavailable in release builds and orphan-node
count is zero in a release export. These values describe Godot's static
allocator, not total Windows process working set. Record the Godot process
working set separately in Task Manager or with `Get-Process` when comparing
system memory.

## Confirmed Windows results

The Windows validation used Godot 4.7.2. The GDScript suite passed 702 tests.
The synthetic soak ran each of the 50, 150, 300, and 500 process scenarios for
300 seconds with seed 2025. Confirmed results:

| Processes | Average FPS | Largest observed frame interval | Invalid snapshots | Orphan nodes |
|---:|---:|---:|---:|---:|
| 50 | 60.00 | — | 0 | 0 |
| 150 | 59.08 | — | 0 | 0 |
| 300 | 57.43 | — | 0 | 0 |
| 500 | 54.39 | 385.62 ms | 0 | 0 |

The benchmark also recorded the DEMO generation, JSON parsing/validation,
selection, and creature reconciliation stages. Their numeric breakdown should
be read from the CSV produced by that run; it was not included in this summary,
so this document does not infer which stage caused the frame peak. The reported
frame interval is a peak observation. Its cause has not been established; it is
recorded as a known performance limitation, not as a confirmed runtime defect.
No fixed FPS threshold is an acceptance criterion.

Godot static memory increased by approximately 4.2–4.4 MiB per scenario. This
is a start/end or per-scenario observation of the static allocator, not a
time-series plateau measurement and not total process working set. By itself,
it neither confirms nor rules out a memory leak. No orphan nodes were observed,
and the maximum of 60 creatures was respected throughout the reported runs.

The instrumented runner includes synthetic JSON serialization and parsing to
measure the HTTP client's parser path. That work is not part of normal DEMO
operation, so its total frame and tick timings are diagnostic and do not exactly
represent ordinary DEMO use. Profiling is opt-in: `DemoSnapshotSource` and
`GardenController` initialize `profiling_enabled` to `false`; only the separate
benchmark runner enables it.

The soak evidence above is recorded. The manual real-API interruption and
reconnection result has not yet been supplied or recorded. E03.2 remains
**awaiting that confirmation**; the synthetic reconnect tests do not replace
stopping and restarting the Windows API while the graphical garden is running.

The benchmark does not make performance claims by itself. Keep the CSV with
the Godot version, Windows build, hardware, renderer, and run duration when
comparing runs. Close unrelated applications or record their presence; do not
compare runs across materially different conditions as if they were identical.

## Windows commands

Run the visual benchmark without `--headless`; the frame-rate measurements
need the normal renderer. The CSV is written under Godot's project user-data
directory and its full path is printed on completion.

```powershell
$godot = 'C:\tools\Godot\Godot_v4.7.2-stable_win64_console.exe'
$project = 'C:\Projects\ProcessGarden'
& $godot --headless --editor --path $project --quit
if ($LASTEXITCODE -ne 0) { throw 'Godot import failed' }
& $godot --headless --path $project --script res://tests/run_tests.gd
if ($LASTEXITCODE -ne 0) { throw 'Godot tests failed' }
Set-Location $project
& $godot --path . --script res://tests/run_benchmark.gd -- --duration-seconds=30 --warmup-seconds=5 --seed=2025
if ($LASTEXITCODE -ne 0) { throw 'Benchmark failed' }
```

By default, the benchmark runs 50, 150, 300, and 500 process scenarios. To
isolate one scenario, add `--scenario=500`. A five-minute pass for each
scenario is:

```powershell
& $godot --path . --script res://tests/run_benchmark.gd -- --duration-seconds=300 --warmup-seconds=30 --seed=2025
```

The recorded soak used 300 seconds per scenario. A longer 15-minute pass can
use `--duration-seconds=900 --warmup-seconds=30`; with all four cases this takes
about one hour plus startup and scenario cleanup. Review node/orphan counts,
the 60-creature cap, invalid snapshots, and memory over time. Start/end memory
alone cannot establish a plateau. Review frame-time p95 and maximum as well as
average FPS; averages alone can hide stutters.

The GDScript suite also repeats REAL/DEMO source changes 20 times with the API
endpoint intentionally unavailable, checks that failures retain the last
valid real registry and creature, and checks that a fresh sample restores the
same creature. This exercises application state deterministically; it does
not replace a graphical Windows run with the actual Python API stopped and
restarted. For that manual check, start the API using the README command,
leave the graphical garden in REAL mode, stop that API with Ctrl+C, and
observe Stale then Disconnected while the creatures remain. Restart the API
with the same command and confirm Connected returns without duplicate
creatures.

## Audit findings before measurement

- `GardenController.update_separation()` checks every represented pair each
  frame: at 60 creatures this is 1,770 pairs. It reuses member arrays, but
  still performs distance and vector calculations. The benchmark is needed to
  establish whether this is material on target Windows hardware.
- Each creature updates local movement, smoothing, breathing, and drawing
  properties every process frame. Its visual selection setter avoids redraws
  when the selection value is unchanged.
- Snapshot reconciliation deep-copies each process record, then the selector
  creates and sorts candidate dictionaries before the garden updates or
  creates nodes. For 500 monitored processes, at most 60 creature nodes are
  represented. Pipeline timing measures parser validation, registry
  reconciliation, selection, and garden reconciliation together.
- Garden changes are snapshot-driven. New creature nodes are only created
  when identities enter the selected set; removed nodes wait for their short
  despawn animation. Source changes detach and queue-free old nodes before
  accepting the new source.

No runtime optimization is justified until measurements show a repeatable
bottleneck. E03.2 remains open until the real API interruption/reconnection
result has been reviewed.
